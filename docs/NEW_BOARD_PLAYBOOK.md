# How to run a PCB project in this workspace (playbook)

Written for: a future Claude session starting fresh here, asked to make a new board. Follow the A-to-Z
checklist below in order; the sections after it explain each step. Details and the failure catalogue are
in `docs/PCB_CREATION_GUIDE.md`; traps already paid for are in `docs/LESSONS_LEARNED.md`.

Worked examples - copy **only `gen/make_pcb.py`** from the closest one, never the shared stages:
- `projects/uno-toggle/` - an Arduino **shield** with firmware and live Wokwi simulation
- `projects/blinky-555/` - a **standalone** board with no MCU, simulated with SPICE
- `projects/reflex-machine/` - the big one (123 parts, Mega + ESP32, full 4-stage test pipeline)

---

## A-to-Z checklist (a new board)

The user works in **small steps**: do one step, show the result, ask before the next.

| # | Step | Produces | Done when |
|---|---|---|---|
| A | Ask the questions in section 1, write the answers | `projects/<id>/DESIGN_BRIEF.md` | user said GO |
| B | Get real pin numbers (`python tools/sym_pins.py Lib:Sym`) and footprint sizes (`python tools/fp_bbox.py Lib:Fp`) | notes / comments | never guessed from a datasheet |
| C | Write the netlist; add a `SPICE = {...}` block if the board has no MCU | `gen/netlist.py` | `python projects/<id>/gen/netlist.py` shows no single-pin nets |
| D | Copy `make_pcb.py` from the closest example, edit its constants block (size, placements, holes, silk) | `gen/make_pcb.py` | - |
| E | `python pipeline.py <id> --only sch,sch-check` | `.kicad_sch` | 0 netlist mismatches, `ERC summary: {}` |
| F | `python pipeline.py <id> --only place,check` - fix placement first | `.kicad_pcb` | no courtyard/hole errors; look at the render |
| G | `python pipeline.py <id> --only route,finish,check` | routed board | **0 errors / 0 unconnected / 0 parity** |
| H | `python pipeline.py <id> --only outputs,fabreport,connections` | `out/fab`, `out/docs`, `MANUFACTURING.md`, `CONNECTIONS.md` | drill cross-check **matches**, 0 pin differences, every copper/hole CHECK explained |
| I | Firmware (if any): sketch + `sim/` PlatformIO build + `test/pinmap.py` | `firmware/`, `sim/` | `pinmap` 0 mismatches |
| J | Simulation: MCU -> Wokwi (`test/wokwi/` + `webview/projects/<id>/wokwi_map.json`); no MCU -> the `spice` stage | test results | real run passes (Wokwi costs quota - ask first) |
| K | `python pipeline.py <id> --only webview`, then write `webview/projects/<id>/io_map.json` (inputs/outputs, **always with `ref`**) and re-run it | 3D view + dashboard | the board loads and simulates in the browser |
| L | Project docs: `README.md` (index), `WIRING_GUIDE.md` if there are off-board wires | user-facing docs | a non-expert could assemble it |
| M | Workspace docs: `CLAUDE.md` status + session log, new traps in `docs/LESSONS_LEARNED.md`, root `README.md` projects list | - | the next session could continue without asking |

After step H the whole chain is one command: `python pipeline.py <id> --list` shows the stages,
`python pipeline.py <id>` runs them all. Once `out/fab` exists it refuses to redo design stages without
`--force` - that protects a signed-off board.

## 0. Orient yourself (2 minutes)
1. `CLAUDE.md` - environment, folder layout, status, session log (auto-loaded).
2. `docs/LESSONS_LEARNED.md` - the traps that already cost time. Do not rediscover them.
3. For an EXISTING board: its `projects/<id>/README.md` first - it indexes everything else.

## 1. Talk to the user BEFORE designing
Ask, and write the answers into `DESIGN_BRIEF.md`:
- What does the machine do; what firmware exists (read it - the pin map is non-negotiable input).
- Supply voltage and current; one supply or several.
- Every actuator/sensor: type, voltage, current, connector preference, cable length.
- **Can they solder surface-mount parts?** If unsure, assume NO and design through-hole. Converting later
  costs a complete re-layout (see LESSONS 17-19). This user cannot - all boards so far are through-hole.
- Which dev boards exactly (a photo or link), and how they mount (shield on top vs sockets).
  **Ask them to measure pin-row spacing with calipers** for any plug-in module not in KiCad's library.
- Board size limits, mounting holes, who assembles it, where it will be made (some fabs only do 1 layer).
Offer a sensible default for each question so the user can answer "default".

## 2. Build from one source of truth
`gen/netlist.py` holds every part: ref, symbol, value, footprint, pin->net map, LCSC number.
Nothing else defines the circuit. Everything downstream is generated by `pipeline.py`:

| Stage | Runs | Gate |
|---|---|---|
| `sch`, `sch-check` | shared `tools/boardgen/make_sch.py`, `check_sch.py` | 0 mismatches, ERC clean |
| `place`, `route`, `finish`, `check` | the project's `gen/make_pcb.py` | 0 errors / 0 unconnected / 0 parity |
| `outputs` | shared `make_outputs.py` | gerber zip, BOM, CPL, STEP, PDF, renders |
| `fabreport` | shared `make_fab_report.py` | `MANUFACTURING.md`, drill file matches |
| `connections` | shared `make_connections.py` | `CONNECTIONS.md`, 0 schematic-vs-copper differences |
| `pinmap` | the project's `test/pinmap.py` | 0 mismatches |
| `spice` | shared `make_spice.py` (only with a `SPICE` block) | every `expect` passes |
| `webview` | `webview/tools/onboard.py` | loads in the browser |

Rules:
- **The shared stages live once in `tools/boardgen/`. Never copy them into a project** - copies diverge
  (LESSONS section 13). If one needs to behave differently, make it configurable.
- **Never hand-edit `.kicad_sch` / `.kicad_pcb`.** Every fix is a code change so it survives the next rebuild.
- **Re-run `sch` after ANY netlist edit**, or PCB parity will scream about the schematic.
- **Look at `out/docs/render_top.png` after every placement change.** Renders catch what DRC cannot:
  connectors facing the wrong way, labels hidden under parts, unreadable silkscreen.
- Stage scripts can print violations and still exit 0 - read the numbers, not the `--- ok` line.

## 3. Placement order that works
1. Connectors on the board edges, each next to the circuit it serves (LESSON 18).
2. One column/block per functional group; leave a 6-8 mm corridor beside any IC whose pins fan out (LESSON 19).
3. Dev boards: antenna over the board edge, USB reachable, nothing tall underneath.
4. Pre-route the links the pour will not manage: IC ground pins across the package, pull-downs to their
   transistor source, a GND bus between blocks that headers would split (LESSONS 20-23).
5. Only then route.

## 4. What "done" means
- ERC 0, netlist compare 0 mismatches.
- DRC: 0 errors, 0 unconnected, 0 schematic-parity issues. Silk warnings are acceptable only when they
  follow from a user choice (e.g. values printed over pads).
- Renders reviewed by eye, top and 3D.
- `out/fab` has the gerber zip, BOM and CPL; `out/docs` has STEP, schematic PDF, renders.
- `MANUFACTURING.md`: drill cross-check says **matches**, every copper/hole **CHECK** resolved or explained.
- `CONNECTIONS.md`: **0 differences**; parts from non-standard libraries hand-checked against the real
  part's pinout (these are the parts no automatic check can vouch for).
- Simulated (Wokwi or SPICE) and visible in the webview.
- `WIRING_GUIDE.md` written for the actual board if anything is wired off-board.
- `CLAUDE.md` status + session log updated; new traps appended to `docs/LESSONS_LEARNED.md`.

## 5. Testing pipeline (before you ship a board off to fab)
Same 4 stages every time, cheapest/most-automatic first. Reflex Machine's `test/` folder
(`projects/reflex-machine/test/`) is the worked example - copy its structure, not its pin numbers.
Each stage validates the *real* design files, never a generic recreation:

1. **Electrical check on the real `.kicad_pcb`.** `kicad` MCP tools directly on the board file:
   `run_drc`, `run_erc`, `analyze_pcb_power_integrity`, `analyze_pcb_signal_integrity`, and
   `find_tracks_by_net` on every net that actually carries a real load current (not just the supply
   rail - the per-load net, e.g. a motor/LED/actuator output, is what matters). Write the result to
   `test/electrical/REPORT.md`.
2. **SPICE.** Whole board with no MCU: the `spice` pipeline stage (`SPICE` block in `netlist.py`).
   Analog sub-circuits of a bigger board: the `kicad` skill's `analyze_schematic.py`, then the `spice`
   skill's `simulate_subcircuits.py` with LTspice - read LESSONS section 8 before trusting a skip/fail.
   Write the result to `test/spice/REPORT.md`.
3. **Functional/logic sim of firmware + wiring (Wokwi).** Generate `diagram.json` from `gen/netlist.py`
   and the firmware's real pin `#define`s. `wokwi-cli lint` first (free). A real run **costs the user's
   quota** (50 min/month) - ask first, keep it short, it is logged in `test/wokwi/USAGE_LOG.md`.
   The token is a Windows USER environment variable (`WOKWI_CLI_TOKEN`); never write it into a file.
   Pin-name traps and CLI quirks: LESSONS section 9.
4. **Physical bring-up.** Once the board exists: a self-test sketch + checklist under `test/bringup/`,
   and `CONNECTIONS.md` as the multimeter beep-test list.

## 6. Onboarding a board into the webview platform
`python pipeline.py <id> --only webview` (runs `webview/tools/onboard.py`: exports the GLB, caches icons,
scaffolds stubs, builds the manifest). Then fill in `webview/projects/<id>/io_map.json` - which nets are
inputs/outputs, their labels, and **always an explicit `ref`** - and run the stage again. Live simulation:
`wokwi_map.json` for an MCU board, or the `SPICE` block (plus `webview/services/spice/service.py`
running) for a board without one. Never edit `webview/app/` or `webview/server/` to add a project - if
that seems necessary, the genericity is broken and the fix belongs in the generator/backend.
Details: `webview/README.md`, `webview/API.md`.

## 7. Working style that kept this fast
- Batch independent work in one turn (edits + lookups + a render read), then one sequential command for
  chains like place -> route -> finish -> check.
- **Anything containing a backslash (regexes, Windows paths) goes through the Edit/Write tools, never a
  bash heredoc** - heredocs silently turned `\1` into a 0x01 byte and `\b` into backspace (LESSONS 14, 17).
- Ask KiCad for facts instead of guessing: courtyard sizes, pad positions, symbol pins, connectivity clusters.
  A small throwaway diagnostic script beats staring at DRC text (write it in the scratchpad, use it, delete it).
- Test frontend changes in a real browser (headless Edge over CDP - LESSONS section 15), not only with curl.
- Tell the user what is running and why, in plain language; keep electronics jargon out of user-facing docs.
